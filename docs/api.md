# Контракт API

Зафиксирован, чтобы интерфейс и расчётное ядро можно было писать параллельно. Живая схема — на `/docs` работающего сервиса (OpenAPI), здесь то, что из неё не видно: смысл полей и договорённости.

Запуск для разработки:

```bash
uv run uvicorn cosmo_net.serving.api:app --reload
```

Фронтенд в разработке ходит на `http://localhost:8000`; CORS для `localhost:5173` уже открыт. В собранном контейнере фронтенд отдаётся тем же приложением, и кросс-доменных запросов не возникает вовсе.

## Как назвать проект в запросе

Любая ручка, которой нужна конфигурация, принимает **ровно один** из трёх способов её указать:

```jsonc
{ "scenario":   { /* сценарий целиком, как в файле */ } }
{ "variant_id": "a1b2c3d4e5f6" }   // сохранённый вариант
{ "bundled":    "01_full_constellation" }  // один из выданных
```

Ни одного — `422`. Это единственное место, где разрешается прислать сценарий inline; всё остальное работает по идентификаторам.

## Ошибки валидации

Любой невалидный сценарий, откуда бы он ни пришёл, даёт `422` с **полным списком** проблем, а не с первой:

```json
{
  "detail": "scenario_invalid",
  "errors": [
    { "field": "design.satellites[7].plane_id", "code": "unknown_plane",
      "message": "Satellite S08 refers to plane 'P9', which is not declared" }
  ]
}
```

- `field` — путь до проблемного поля, годится для подсветки в форме.
- `code` — стабильный идентификатор, **его и переводит интерфейс**.
- `message` — английский текст на случай кода, которому ещё нет русской формулировки.

Коды: `unsupported_schema`, `malformed_json`, `not_an_object`, `duplicate_id`, `unknown_plane`, `unknown_satellite`, `unknown_gateway`, `id_collides_with_satellite`, `no_client`, `no_gateway`, `step_exceeds_horizon`, `horizon_not_multiple_of_step`, `interval_before_zero`, `interval_not_positive`, `interval_past_horizon`, плюс коды pydantic для проблем формы (`int_type`, `greater_than_equal`, …).

## Ручки

| метод и путь | назначение |
|---|---|
| `GET /api/health` | статус, версия, собран ли фронтенд, список выданных сценариев |
| `GET /api/scenarios` | краткие карточки выданных сценариев для выбора |
| `GET /api/scenarios/{name}` | выданный сценарий целиком |
| `POST /api/scenarios/validate` | проверить файл, не запуская расчёт |
| `GET /api/variants` | сохранённые варианты, новые первыми |
| `POST /api/variants` | сохранить вариант: `{label, …ссылка на проект}` → `201 {id}` |
| `GET /api/variants/{id}` | вариант со сценарием |
| `DELETE /api/variants/{id}` | удалить, `204` |
| `POST /api/runs` | расчёт: `{…ссылка, strategy?, save_as?}` |
| `GET /api/runs/{id}` | тот же ответ ещё раз |
| `GET /api/runs/{id}/snapshot?t_s=` | состояние сети в один момент |
| `GET /api/runs/{id}/trajectory` | положения и связи на **все** шаги, одним ответом |
| `GET /api/runs/{id}/export` | выгрузка `cosmo-A-result-1.0`, отдаётся файлом |
| `POST /api/compare` | `{run_ids: [...], labels?}` → таблица и дифф параметров |
| `POST /api/analysis/criticality` | ранжирование аппаратов по цене их потери |
| `POST /api/analysis/sweep` | перебор конфигураций, `{mode: "spacing" \| "refine"}` |

`strategy` — одно из `min_hops` (по умолчанию), `min_distance`, `max_margin`.

## Ответ расчёта

Прогон возвращается **целиком**, включая маршрут на каждом шаге. Для базового сценария это около 200 КБ до сжатия и порядка 30 КБ после gzip, который включён. Ползунок времени за счёт этого перерисовывается из памяти, а не 720 запросами к серверу.

```jsonc
{
  "run_id": "61945a68c3a7",
  "variant_id": null,              // заполнен, если был save_as
  "times_s": [0, 120, …],          // 720 значений
  "summary": {
    "worst_availability": 0.9667,  // доли единицы, не проценты
    "worst_max_gap_s": 480,
    "meets_target": true,
    "target_availability": 0.9,
    "clients": [ /* те же метрики плоским списком */ ]
  },
  "clients": {
    "C65": {
      "metrics": {
        "availability_share": 0.9667, "visibility_share": 0.9778,
        "max_gap_s": 480, "max_interior_gap_s": 480, "gap_count": 19,
        "mean_hops": 2.29, "max_hops": 5, "mean_route_length_km": 3151.5,
        "meets_target": true,
        "causes": { "no_client_contact": 16, "no_gateway_contact": 8 }
      },
      "reachable": [true, …],      // 720
      "cause":     ["none", …],    // 720
      "hops":      [2, …],         // 720, null где маршрута нет
      "path":      [["C65","S20","G_MUR"], …],  // 720, [] где маршрута нет
      "gateway":   ["G_MUR", …],   // 720, null где маршрута нет
      "length_km": [1834.2, …],    // 720, null где маршрута нет
      "gaps": [
        { "start_s": 59400, "end_s": 59520, "duration_s": 120,
          "cause": "no_client_contact", "causes": {"no_client_contact": 1},
          "at_horizon_edge": false }
      ]
    }
  },
  "scenario": { /* сценарий, которым реально считали */ },
  "outage_causes": ["no_client_contact","gateway_offline","no_gateway_contact","network_split"]
}
```

Договорённости, на которые можно опираться:

- Все массивы длины `times_s` и **индексируются одним и тем же шагом**. Проверять длину не нужно, проверять согласованность — тоже: `path[i]` непуст тогда и только тогда, когда `reachable[i]`.
- `cause[i] == "none"` там, где маршрут есть.
- Доли — в долях единицы. В проценты переводит интерфейс.
- Перерыв покрывает интервал `[start_s, end_s)`; один пропущенный шаг длится `step_s`, а не ноль.
- `at_horizon_edge` — перерыв упирается в край расчёта, его настоящая длина неизвестна. Показывать отдельно.

### Четыре причины перерыва

Порядок важен: называется **первое** условие, блокирующее путь, иначе диагноз отправит инженера чинить не тот конец линии.

| код | что произошло |
|---|---|
| `no_client_contact` | над клиентским пунктом нет ни одного работающего аппарата |
| `gateway_offline` | все шлюзы в объявленном отказе |
| `no_gateway_contact` | шлюзы работают, но над ними нет аппаратов |
| `network_split` | оба конца видят аппараты, но цепочки связей между ними нет |

## Траектория целиком

`GET /api/runs/{id}/trajectory` — то, чем рисуется карта. 247 КБ в gzip на базовый сценарий, 175 мс на сборку.

```jsonc
{
  "times_s": [0, 120, …],          // 720
  "step_s": 120,
  "satellite_ids": ["S01", …],     // 48
  "plane_ids":     ["P1", …],      // параллельно satellite_ids
  "ecef_km":  [ [[6770,-1439,0], …48], …720 ],   // гринвичские, целые км
  "active":   [ [true, …48], …720 ],
  "links":    [ [[12,13], …], …720 ],            // индексы в satellite_ids
  "ground_visible": { "C65": [ [18,19], …720 ] },// индексы аппаратов
  "ground_sites": [ /* как в сценарии */ ]
}
```

**Почему не по шагам.** Сначала карта тянула `snapshot` на каждый кадр. При проигрывании запросы не успевали и глушили друг друга: аппараты стояли на устаревшем кадре, а маршрут, который лежит в памяти, уже уехал вперёд — картинка противоречила сама себе. Один ответ на 247 КБ дешевле, чем 720 ответов по 20 КБ, и он единственный, который можно рисовать не дожидаясь сети.

**Почему ECEF, а не широта с долготой.** Между шагами положения интерполируются: шаг 120 с — это 908 км, без интерполяции получается стробоскоп. Интерполировать декартовы векторы и переводить в градусы при отрисовке — значит не возиться с переходом через 180-й меридиан и с полюсами. Ошибка хорды против дуги 15 км, меньше пикселя.

## Состояние сети в момент времени

`GET /api/runs/{id}/snapshot?t_s=3600` — пересчитывается на лету, около миллисекунды. Интерфейсом не используется (он берёт траекторию целиком), но остаётся в API: это самый прямой способ спросить состояние сети в один момент, вместе с углами возвышения.

```jsonc
{
  "t_s": 3600,
  "satellites": [{ "id": "S01", "x_km": …, "y_km": …, "z_km": …,
                   "lat_deg": …, "lon_deg": …, "plane_id": "P1", "active": true }],
  "links":        [{ "a": "S01", "b": "S02", "distance_km": 2700.1 }],
  "ground_links": [{ "site": "C65", "satellite": "S20",
                     "distance_km": 1834.2, "elevation_deg": 41.7 }],
  "elevation_deg": { "C65": { "S01": -32.4, … } },
  "ground_sites": [ /* как в сценарии */ ]
}
```

Координаты гринвичские (ECEF): Земля неподвижна, аппараты движутся. `lat_deg`/`lon_deg` посчитаны из них же — для карты нужны только они.

## Сравнение

```jsonc
{
  "comparable": true,               // false, если у прогонов разная сетка времени
  "grids": [[86400, 120]],
  "runs":    [{ "label": "база", "worst_availability": 0.9667, "meets_target": true, … }],
  "clients": [{ "client_id": "C65", "cells": [ {…}, {…} ] }],  // cells по порядку runs
  "changes": [{ "path": "design.planes[P2].raan_deg", "before": 60.0, "after": 65.0 }]
}
```

`changes` сопоставляет элементы списков **по идентификатору**, а не по позиции: переставленный список аппаратов изменением не считается. При `comparable: false` таблицу показывать нельзя — надо сказать, что сетки разные.

## Перебор конфигураций

```jsonc
{
  "baseline":  { "raan_deg": [0,60,120], "phase_deg": [0,7.5,15],
                 "worst_availability": 0.9667, "worst_max_gap_s": 480,
                 "availability": { "C65": 0.9667, … } },
  "best":      { … },
  "frontier":  [ … ],   // фронт Парето: доступность против макс. перерыва
  "candidates":[ … ]    // всё перебранное, для облака точек
}
```

Исходная конфигурация **всегда** присутствует среди `candidates`, поэтому `best` не может оказаться хуже, чем ничего не менять. `frontier` отсортирован по убыванию доступности и по возрастанию качества перерыва; на сценарии 01 он схлопывается в одну точку, на 04 содержит четыре — это и есть материал для графика.

## Чего в API нет и почему

- **Нет пошаговых запросов маршрута.** Пробовали первым делом; ползунок ощущается ровно так медленно, как звучит.
- **Прогоны не хранятся на диске.** Это 124 мс арифметики над сохранённым вариантом, в памяти живут последние 32. Просроченный `run_id` даёт `404` с текстом про пересчёт — интерфейс должен уметь просто запустить расчёт заново.
- **Варианты хранятся в SQLite** и переживают перезапуск: терять сохранённую конфигурацию из-за передеплоя в день защиты нельзя.
